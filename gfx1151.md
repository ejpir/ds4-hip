# gfx1151 DeepSeek-V4-Flash / CyberNeurova GGUF Notes

Verified against the CyberNeurova abliterated DeepSeek-V4-Flash Q2_K GGUF and
`ds4.c`. Target GPU observed in this repo is `gfx1151` / AMD Radeon 8060S
Graphics.

Unless a section explicitly says `ds4_hip.cpp` legacy HIP path, these notes apply
to the ROCm upstream-shaped build as well: `ds4_cuda.cu` compiled with `hipcc`
through `ds4_rocm.h` and linked into `ds4-rocm-upstream`,
`ds4-server-rocm-upstream`, and `ds4-bench-rocm-upstream`.

## Model identity

The CyberNeurova artifact is not a generic DeepSeek V3/V3.2-style shape. It is
`general.architecture = deepseek4`, based on `deepseek-ai/DeepSeek-V4-Flash`.

Fixed metadata:

- Layers: 43
- Embedding dim: 4096
- Vocab: 129280
- Context: 1048576
- Attention heads: 64
- KV heads: 1
- Key/value dim: 512 / 512
- Q/O LoRA ranks: 1024 / 1024
- Output groups: 8
- Sliding window: 128
- MoE experts: 256 total, 6 active, 1 shared
- Expert FF dim: 2048
- Indexer: 64 heads, head dim 128, top-k 512
- Compression ratios: layers 0..1 uncompressed, then alternating ratio 4 and
  ratio 128 through layer 42. Ratio-4 layers have the indexer stream.

## MLA / attention projection structure

Per layer core attention tensors, GGUF stored order:

```text
q_a           Q8_0 [4096, 1024]
q_b           Q8_0 [1024, 32768]   # 64 * 512 query fan-out
kv            Q8_0 [4096, 512]     # single KV latent/head
attn_output_a Q8_0 [4096, 8192]    # grouped 8 * rank 1024
attn_output_b Q8_0 [8192, 4096]
```

Core attention projection tensor ops are five GEMM-like projections per layer:
`q_a`, `q_b`, `kv`, `output_a`, `output_b`. If `output_a` is implemented as
8 grouped GEMMs internally, kernel tiling count changes, but tensor-level count
is still five.

The `kv [4096, 512]` tensor is about 2.13 MiB in Q8_0 storage:

```text
4096 * 512 = 2,097,152 params
Q8_0 storage = params * 34/32 = 2,228,224 bytes = 2.13 MiB / 2.23 MB
```

Exact core attention params per layer:

```text
q_a      4096*1024      =  4.19M
q_b      1024*32768     = 33.55M
kv       4096*512       =  2.10M
out_a    4096*8192      = 33.55M
out_b    8192*4096      = 33.55M
total                    = 106.95M params/layer
```

Q8_0 storage for core attention:

```text
106.95M params * 34/32 = 108.38 MiB/layer
43 layers              = 4.55 GiB
```

Core attention is therefore the dominant Q8_0 weight block. Total Q8_0 params in
this file are about 7.261B.

## Active parameter estimate

Approximate params touched per token:

```text
core attention projections       4.599B
routed top-6 experts             6.493B
shared expert                    1.082B
attention compressors            0.261B
indexer path                     0.226B
embeddings + output              1.059B
router + HC/small                ~0.08B
```

Including embedding/output, this lands around 13.8B params touched. Excluding
embedding/output as transformer active params, it is closer to 12.7B.

Indexer path detail:

```text
indexer.attn_q_b [1024,8192] = 8.39M params/layer
full indexer path/layer      = ~10.75M
21 ratio-4 layers            = ~226M
```

MLP active MACs per token:

```text
routed: 6 * 3 * 4096 * 2048 * 43 = 6.493B MACs
shared: 1 * 3 * 4096 * 2048 * 43 = 1.082B MACs
total MLP = 7.575B MACs ≈ 15.15 GFLOPs/token if counting 2 FLOPs/MAC
```

So ~27 GFLOPs/token is closer to whole active weight-matmul cost, not MLP alone.

## Compression and attention cost

Compression pattern:

```text
layers 0..1: no compression
even layers 2..42: ratio 4 + indexer, 21 layers
odd layers 3..41: ratio 128, 20 layers
```

Ratio-128 attention is bounded much better than raw full attention, but is not
constant-cost. For ratio-128 layers, visible rows are approximately:

```text
128 raw sliding-window rows + P/128 compressed rows
```

Ratio-4 layers attend over approximately:

```text
128 raw rows + up to top_k=512 selected compressed rows
```

The ratio-4 attention itself is bounded after top-k, but indexer scoring/top-k
grows with compressed history.

For ratio-4 layers, compressed rows are `P/4`, not `P`. Naive per-head indexer
score MACs across all 21 ratio-4 layers:

```text
21 * P * (P/4) * 64 * 128 = 43,008 * P^2 MACs
```

At `P = 32768`, this is about:

```text
~44T MACs, or ~88 TFLOPs if counting 2 FLOPs/MAC
```

The local HIP path has a `qmix` fast path that mixes heads first and reduces the
score dot product to `head_dim=128`, so actual score FLOPs can be much lower;
top-k and memory traffic may still dominate.

## gfx1151 tuning implications

The main shapes worth tuning are fewer than the raw tensor count suggests:

- Q8_0 dense attention: `[4096,1024]`, `[1024,32768]`, `[4096,512]`,
  `[4096,8192]`, `[8192,4096]`.
- Q8_0 shared expert: `[4096,2048]` gate/up and `[2048,4096]` down.
- Q2_K routed expert grouped GEMM: gate/up `[4096,2048]` and down
  `[2048,4096]`, batched over 256 experts with top-6 active routing.
- Indexer: `[1024,8192]`, `[4096,64]`, `[4096,256]`, plus score/top-k.

Pathological small-N shapes such as `[4096,64]`, `[1024,4]`, `[256,4]`, and
`[16384,24]` are poor WMMA targets. They are mostly small enough that heavy
tuning is lower priority than MoE, output projection, and indexer/top-k.

`attn_output_a` and `attn_output_b` are not small. Together they are
67.1M params/layer, bigger than `q_a + q_b` combined. They are different shapes
and should be tuned separately.

The highest-impact kernel work is expected to be the fused routed MoE path:

- group tokens by expert,
- compute gate + up,
- apply SwiGLU and route weight,
- compute down,
- avoid unnecessary materialization and memory traffic.

The shared expert is always-on Q8_0 and well-shaped. It is an easy dense-GEMM
performance floor and can potentially overlap with routed-expert dispatch on a
separate stream while routing/sorting is in flight.

Ratio-4 and ratio-128 layers deserve distinct attention/compressor paths:

- Ratio-4: bounded attention after top-k, but indexer scoring/top-k is the
  long-context bottleneck.
- Ratio-128: attention grows only with `P/128` compressed rows plus 128 raw rows;
  this is much cheaper and should not share all assumptions with ratio-4.

## HC function tensors

`HC fn` is Manifold-Constrained Hyper-Connections, not a classifier, hash head,
or speculative-decoding head.

It runs twice per layer, every token:

```text
hc_attn_fn before attention
hc_ffn_fn  before FFN
```

Each maps:

```text
4 * 4096 = 16384  ->  24
```

The 24 values become HC mixing/control values: pre weights, post weights, and a
4x4 mixing matrix after Sinkhorn. It affects prefill, but the total parameter
count is small:

```text
86 * 16384 * 24 = 33.88M params total
```

N=24 is a bad WMMA shape, but it is not worth major tuning compared with routed
MoE, attention output projection, and indexer/top-k.

## Decode bandwidth model

Decode is a different regime from prefill. At batch 1, weight reads are not
amortized across many tokens, so the practical upper bound is mostly bytes read
per token divided by memory bandwidth. Compute still matters for bad kernels and
small random expert reads, but the first-order limit is bandwidth.

GGUF storage byte assumptions:

```text
Q8_0 = 34/32 bytes/param
Q2_K = 84/256 bytes/param
```

Approximate active weight bytes per decode token, assuming Q8_0 tensors are read
in their GGUF Q8_0 storage layout by Q8 kernels:

```text
core attention q8       4.886 GB
routed top-6 q2         2.130 GB   # 1.984 GiB
shared expert q8        1.150 GB
attn compressors q8     0.278 GB
indexer path q8         0.240 GB
router f32              0.180 GB
output projection q8    0.563 GB   # input token embedding row is negligible
HC fn q8                0.036 GB
--------------------------------
total                   9.46 GB/token
```

The ROCm upstream-shaped path can optionally cache/dequantize selected Q8_0
weights as FP16 for cuBLAS/hipBLASLt-style kernels, controlled by `DS4_CUDA_*`
flags such as attention-output or shared-expert preload/cache options. In that
mode actual HBM traffic for those tensors is closer to 2 bytes/param from the
FP16 cache, not 34/32 bytes/param from GGUF Q8_0 storage. The table above is
therefore the Q8-kernel byte model, not a guarantee for every optimized ROCm
configuration.

So a short-context decode upper bound at 225 GB/s effective memory bandwidth is:

```text
225 / 9.46 ~= 23.8 tok/s
```

The routed Q2_K choice is important for decode. Active routed experts are about
2.13 GB/token in Q2_K. If those same active expert weights were Q8_0, they would
be about 6.90 GB/token, raising the total active weight bytes to about
14.2 GB/token. Q2_K is therefore a ~3.2x byte reduction for the routed experts
specifically, not a 9.2 GB -> 21 GB whole-token jump.

## Decode KV/cache traffic

Do not model decode cache traffic as `43 * C * 512 * bf16`. In the current DS4
GPU graph, cache tensors are allocated/read as `float` buffers. Some values are
f16- or FP8-rounded before storage, but the storage slot is still 4 bytes.

Decode also does not read all `C` rows for every layer:

- Raw SWA reads at most the latest 128 rows per layer.
- Ratio-4 layers read raw rows plus up to top-k 512 selected compressed rows.
- Ratio-128 layers read raw rows plus approximately `C/128` compressed rows.
- The indexer scans ratio-4 index rows of dim 128 when compressed rows exceed
  top-k.

Idealized lower-bound cache bytes per decode token, assuming good row reuse and
not counting repeated per-head rereads inside a kernel:

```text
context       cache bytes/token lower bound
4k            ~0.046 GB
32k           ~0.132 GB
128k          ~0.418 GB
512k          ~1.57 GB
1M            ~3.19 GB
```

With 225 GB/s and the 9.46 GB/token active-weight estimate, the idealized decode
upper bounds are roughly:

```text
context       total bytes/token   upper-bound tok/s
short         9.46 GB             23.8
32k           9.59 GB             23.5
128k          9.88 GB             22.8
512k          11.03 GB            20.4
1M            12.65 GB            17.8
```

These are upper bounds. Real gfx1151 decode can be much lower because routed
expert reads are sparse/random, router decisions happen mid-forward, Q2_K must
be dequantized, and launch/synchronization overhead is visible at batch 1. A
well-tuned short-context target around 12-15 tok/s is plausible; a naive or
generic-kernel path can be much lower.

Allocated KV/cache capacity is not the same as per-token read traffic. At 1M
context the graph can allocate tens of GB of cache due to raw capacity,
compressed capacity, indexer cache, state buffers, and scratch, but decode reads
only the visible raw/compressed/index rows for the current token.

## Decode-specific tuning notes

- Fuse decode kernels aggressively. At 10-20 tok/s, hundreds of tiny launches per
  token become measurable even if bandwidth dominates.
- The fused routed MoE decode path is still high priority: route, load only the
  top-6 expert rows, compute gate/up, SwiGLU, and down with minimal
  materialization.
- The shared expert is always-on Q8_0 and well-shaped. It can potentially overlap
  with routed-expert dispatch or routing/sorting work.
- Expert prefetch matters because the selected experts are not known until the
  router runs. Predicting likely next-layer experts or issuing prefetch as soon
  as router output is available can hide latency even though it does not reduce
  bytes read.
- Speculative decoding is the main path to exceed the single-token bandwidth
  upper bound. DeepSeek-V4 metadata includes `nextn_predict_layers = 1`, and DS4
  has optional MTP support, but the current MTP path is experimental and should
  not be confused with HC.
- `HC fn` tensors are hyper-connection control projections, not Medusa/MTP
  speculative heads.

## Indexer top-k paths: legacy HIP vs ROCm upstream-shaped

The decode path is still not fused for indexer scoring and top-k. It materializes
`indexer_scores`, launches an indexer top-k kernel to produce `comp_selected`,
then runs indexed attention using the selected compressed rows. The proper
long-term fix is a fused indexer score + streaming top-k kernel that never writes
and rereads the full score matrix.

This repo currently has two GPU backend shapes:

- Legacy/default HIP build: `ds4_hip.cpp`, linked into `./ds4` when `HIPCC` is
  available.
- ROCm upstream-shaped build: `ds4_cuda.cu` compiled with `hipcc` via
  `ds4_rocm.h`, linked into `./ds4-rocm-upstream`, `./ds4-server-rocm-upstream`,
  and `./ds4-bench-rocm-upstream`.

The earlier `n_comp <= 8192` cliff applies to the legacy `ds4_hip.cpp` path, not
to the upstream-shaped ROCm path.

### Legacy `ds4_hip.cpp` path

`ds4_hip.cpp` uses `ds4_hip_indexer_topk_iter_parallel_kernel` only when:

```text
n_comp <= 8192 && top_k <= 1024
```

For larger `n_comp`, it falls back to `ds4_hip_indexer_topk_kernel`, a one-thread
per-token implementation that rereads the score row from HBM roughly
`top_k * n_comp`. With `top_k = 512`, this is a severe decode cliff once ratio-4
compressed rows exceed 8192, i.e. around `context ~= 8192 * 4 = 32768` tokens.

If the legacy HIP path still matters, a safe temporary patch is to raise the fast
threshold to `n_comp <= 15360` with the existing 256-thread launch:

```text
LDS bytes = 4 * n_comp + 8 * threads
n_comp = 15360, threads = 256 -> 63488 bytes
```

This leaves about 2 KiB margin under the observed gfx1151 64 KiB LDS limit and
pushes the legacy cliff to about 61k context. It is only a cliff-raiser; it does
not solve 128k+ or 1M context.

### ROCm upstream-shaped `ds4_cuda.cu` path

The upstream-shaped path already has a better top-k tree in
`ds4_gpu_indexer_topk_tensor`:

```text
n_comp <= 1024   -> indexer_topk_1024_kernel
n_comp <= 2048   -> indexer_topk_pow2_kernel<2048>
n_comp <= 4096   -> CUB/hipcub or indexer_topk_pow2_kernel<4096>
n_comp <= 8192   -> CUB/hipcub or indexer_topk_pow2_u16_kernel<8192>
n_comp > 8192    -> chunked 4096-row top-k + tree merge, by default
```

For `top_k = 512`, the `n_comp > 8192` chunked path is enabled unless disabled by
environment knobs such as `DS4_CUDA_NO_TOPK_CHUNKED`. It reads the score row in
chunks and merges top-k candidates; it does **not** fall directly into the
`top_k * n_comp` one-thread fallback at 32k context.

So for the ROCm upstream-shaped path, the immediate issue is not the old 8192
threshold. The remaining issue is score materialization itself: the score kernel
writes `n_tokens * n_comp` floats to memory, and top-k reads those scores back
plus candidate scores during merge. That is much better than the legacy fallback,
but still inferior to a fused score+streaming-top-k decode kernel.
